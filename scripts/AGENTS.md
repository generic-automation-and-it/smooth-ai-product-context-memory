# AGENTS.md - Operational Scripts

## TL;DR

Operational checks support operator decisions; a preflight must never repair the corpus it inspects.

## Non-Negotiables

- Ticket ownership preflight is read-only, including against the default dev database. Never weaken the migration's duplicate guard or choose a keeper automatically.
- Exact provider/key and group UUID reports are sensitive operational output, not application logging. Never send them to telemetry, CI artifacts, or commits; credentials stay inside the container.
- API smoke credentials are generated per run, passed through environment variables, used only in
  Authorization headers, and never printed or committed.
- Verification uses a newly created isolated fixture, never the default corpus or a schema cloned from it. Cleanup may remove only resources created by that test invocation.
- Do not turn the manual remediation runbook into an automated destructive cleanup script. Membership ownership is an operator decision; preserving memories does not preserve ticket-based discoverability.

## Key Behaviors

- `run.sh` / `run.ps1` are **operator launchers, not checks**, and are the only scripts here that are meant to be run as a daily entry point rather than as a verification. Each starts exactly one container — the published controller image, which carries the AppHost, DCP and dashboard — and that controller starts the other four workloads through the mounted socket. Nothing in this directory may start `mimisbrunnr-<id>-{host,postgres,blob-well,seq}` directly: their ownership, health and lifecycle rules live in `apphost-container-entrypoint.sh`, and a launcher that bypassed them would re-create open defect #159 (a second controller removing another installation's running workloads). Documented in [CONTROLLER_LAUNCHER.md](CONTROLLER_LAUNCHER.md).
- **Credential resolution is environment → stored file → adopt-provisioned → generate, and the file is only ever added to.** Never rewrite a stored secret and never drop a key that is already there. Release mode binds the tokens into the running Host, so rotating one 403s every client holding the old value — which is exactly what an earlier draft did, by persisting only the values the current run selected. A value supplied through the environment is used and deliberately *not* written to disk, because writing a secret the operator did not ask to store is the surprise rather than the omission. **Adoption sits between the stored file and generation, and it resolves the two tokens as a matched pair or not at all** — per-key resolution could adopt one and mint the other, which is the same split-pair 403 the adoption exists to prevent.
- **`env-export` prints credentials, and `up` never does.** `scripts/run.sh env-export [posix|powershell]` emits `export KEY='v'` or `$env:KEY = 'v'` for the `CONTEXT_MEMORY_*` names only — the controller's `Parameters__*` names cannot be assigned by any shell. Printing is a separate verb on purpose: a token written to a terminal that gets scrolled back, recorded, or read over a shoulder is disclosed, so the operator chooses to run it and chooses where it goes. A real environment variable already beats the machine file in the clients, so exporting changes where the value is read from, not which value it is. Diagnostics go to **stderr** throughout: stdout is a data channel that `env-export` is captured from, so a status line written there becomes a command the shell tries to run.
- **The launcher must not depend on `openssl`.** `secret()` prefers it and falls back to `/dev/urandom` through `od`. openssl is declared by neither Dockerfile, so relying on it alone made credential generation fail on a minimal image — and the failure surfaced as an *empty credential file*, not as a missing command, which is why it took a second run on a stock `ubuntu` container to read. The same container run found a second defect the developer's machine could not: `adopted` was declared without a value and only ever incremented on the adoption path, so `set -u` aborted on a fresh clone or a container with no provision file. A checkout that has run the provisioner hides that case permanently. **Run `scripts/test-run-launcher.sh` inside a minimal `ubuntu:24.04` container, not only on the development machine** — it has no openssl, and that is the point.
- **`scripts/test-run-launcher.sh` is the harness, and it must redirect `MIMIS_MACHINE_CREDENTIALS` as well as `MIMIS_HOME`.** The machine-credential path derives from the data home; a harness that redirected only the home wrote to the operator's real `~/.mimisbrunnr` and overwrote live credentials. That was a real defect, found by the harness's first run. Every future case inherits `run_launcher`, which sets both.
- **Both launchers gate on `/health`.** `up` waits for the API and exits non-zero with the cause ranked, because returning immediately made "the script ran" and "the app started" indistinguishable — one bad postgres password once looked like three session restarts' worth of mystery. Neither launcher may drop this gate.
- **Orphan cleanup keys on `io.smooth-mimisbrunnr.installation`.** A hard kill can leave the four workloads with no controller owning them; the launcher removes exactly those carrying its installation's label, and never a container it does not own. A foreign container on one of the names is refused by the controller's own preflight instead.
- **Two file-safety rules both launchers enforce, both of which a first draft got wrong.** `[ -f ]` follows a symlink, so the "not a regular file" guard has to test the link itself (`-L` / `LinkType`) or it passes a symlinked credential file. And mode 600 is re-asserted on *every* run, not only on creation, because reuse is the quiet path where a file widened by a backup restore would otherwise stay group-readable for the life of the installation. Credentials are written through a temp file and renamed, and a temp file holding a secret is removed on interrupt.
- **The token parameters cannot be exported by a shell.** `Parameters__api-read-token` contains hyphens, so `export`/`VAR=x cmd` is a syntax error in both bash and zsh; use `env 'NAME=value' …` or PowerShell's `$env:` provider. Same property as the `#!/bin/bash` entrypoint shebang below, and the reason the generated secrets must reach the container by `--env-file`.

- `release_policy.py` permits publication only for `push` on `refs/heads/main`. PRs, tag pushes, releases, and manual dispatch fail closed. Candidates include source SHA/run/attempt; stale main builds cannot promote `latest`. No version-tag or GitHub Release creation path remains.
- A clean snapshot is not a reservation: writers must remain stopped from the final precheck through migration. Host startup applies migrations, so checking after startup is too late.
- Same-group repeated memberships are not cross-group ownership conflicts. Malformed containers or identity types block preflight even though some live reads treat them as absent; silently skipping them would claim migration readiness without establishing it.
- The checker needs only `public.memory_group`, not AGE or the ticket migration. The [ticket migration runbook](../docs/hlds/003-graph-edges-on-age/ticket-migration-runbook.md) targets legacy data before graph backfill; it refuses installed/partially installed ticket graph objects.
- The one-shot `restore` verb's built-in reconciliation supersedes `scripts/verify-graph-restore.sh` for the HLD 001 NFR-03 round-trip: it restores both stores from a self-verifying snapshot archive and prints a reconciliation (counts, blob resolution, bounded traversal) instead of `pg_dump`/`pg_restore` around `docker exec`. `verify-graph-restore.sh` remains for a lighter graph-only round-trip and `seed-graph-sample.sh` still seeds the NFR-03/NFR-04 checks; the separate NFR-04 pre-upgrade check (`verify-graph-preupgrade.sh`) is unaffected.
- `apphost-container-entrypoint.sh` declares `#!/bin/bash` rather than the `#!/usr/bin/env bash` used by the other scripts in `scripts/`. **That divergence is deliberate; do not normalise it away.** `Dockerfile.apphost` installs the script as `/usr/local/bin/mimisbrunnr-orchestrator` and makes it the container `ENTRYPOINT`, so the shebang *is* the interpreter selection, and an absolute path avoids depending on `env` being on `PATH` at exec. The choice is load-bearing rather than cosmetic: the engine hands the controller `Parameters__api-read-token` / `Parameters__api-write-token`, and dash drops env names that are not shell identifiers — the silent cause of every failed publish between 2026-09-17 and 2026-10-01 (see the changelog). **The consequence to carry forward is that `/bin/bash` is a base-image requirement of `mcr.microsoft.com/dotnet/aspnet:10.0`, not an assumption:** a bash-less aspnet-derived base would fail at container start rather than degrade, and the aspnet image's shell inventory is asserted nowhere in this repository — the publish-image smoke is the only check that would catch it, so treat a base-image change as a publish-blocking change until that smoke runs.
- `provision-credentials.sh` writes the API Bearer tokens to **two** gitignored env files, split by parser grammar: `.context/mimisbrunnr.env` is sourceable and carries only valid shell identifiers (the server `ApiAccess__*` names and the skill `CONTEXT_MEMORY_*` names), and `.context/mimisbrunnr.env.controller` carries the `Parameters__*` names for the published controller's `--env-file` — those names are not shell identifiers, so keeping them in the sourceable file makes `set -a && source` print a token as "command not found". Both files carry the same token values, so the service and the host-side skills still read one source of truth. Idempotent once the pair exists: re-runs reuse the existing values, `--rotate` regenerates, and a pre-split single file (no `.controller`, or still carrying `Parameters__*` lines) is rewritten into the pair rather than silently kept — re-splitting carries the file's existing token values forward, so the documented no-`--rotate` path never rotates a token a running Host already holds. Only a missing file or an explicit `--rotate` regenerates. Mode 600, re-asserted on every reuse run, not only on create. The tokens are runtime configuration only and never touch the store, so rotating them invalidates no data.
- `provision-credentials.sh --base-url` is **shell input**, because consumers `source` the file it lands in: it must be a bare `http(s)` origin (host name, IPv4 or bracketed IPv6, optional port), and anything else — userinfo, a path, `$(…)`, a backtick, `;`, whitespace — is refused without being echoed. The line stays **unquoted on purpose**: the same file is the standalone Host's `docker run --env-file`, which keeps quote characters as part of the value, so validation (whose accepted character set has nothing a shell assignment expands) is the defence, not quoting. A file's existing base URL is kept across a re-split and a `--rotate` that do not name one (re-validated, refused if hand-edited into something else), and naming a different one rewrites the pair keeping the tokens. `--rotate --skip-apphost` warns loudly when the AppHost user secrets still hold the previous pair, checking key names only. A temp file that may hold a token is removed on exit and on `HUP`/`INT`/`TERM`.

## Test References

- Release policy: `python3 scripts/test_release_policy.py`; negative event/ref matrix, fail-closed identity, and stale-main alias tests. Runs in the PR gate's "Test release policy" step.
- Operational harness: `python3 scripts/tests/test_ticket_ownership.py`; mocked Docker transport checks require no daemon.
- Credential provisioner: `bash scripts/test-provision-credentials.sh`; runs the provisioner into a scratch `--env-file` and asserts that sourcing it prints nothing (no token as "command not found"), that `CONTEXT_MEMORY_*` is exported, that the sourceable file carries **no** `Parameters__*` line, and that the `.controller` file carries both `Parameters__api-*-token` names **and nothing else**. Runs in the PR gate's "Test credential provisioner" step. Covers the create path plus the reuse, `--rotate` and pre-split migration paths — a plain re-run must reuse the existing token values, and a re-split must rewrite the pair while carrying them forward. Also covers: a `--env-file` path git does not ignore is **refused** (and the `--allow-unignored-env-file` override works); files are owner-only under a permissive umask; a corrupt or identical-token reuse file is refused rather than propagated; and the AppHost user secrets carry the token without it ever being an argv element. Further: a hostile `--base-url` (command substitution, backtick, `;`, userinfo, path, other scheme, whitespace, empty) is refused with no file written and nothing executed, while bare origins including `[::1]` round-trip through `source`; a hand-edited hostile base URL is refused on reuse; a custom base URL survives a re-split and a `--rotate`, and a new one rewrites without rotating; a file widened to 644 is back to 600 after a reuse run; `--rotate --skip-apphost` warns about stale user secrets without printing a token, and a plain reuse does not; a failed user-secrets write leaves no `.secrets.*` temp file. Every run uses a scratch `HOME`, so the operator's real user-secrets store is never read or written, and a `.context/` directory the harness had to create is removed on exit.

The ignore-refusal coverage is **three** cases, because `check-ignore` gives two different non-zero answers and the guard acts on both: a path *inside* the repository that git does not ignore (exit 1 — the case the guard exists for, asserted on `check-ignore`'s own exit code rather than on the provisioner's message, since both refusals print the same text), a path inside the repository that git *does* ignore (the accept branch, permitted with no override — otherwise the harness's own `provision()` helper would leave the guard untested on the ten calls that pass `--allow-unignored-env-file`), and a path outside the repository, which git cannot answer for (exit 128). The in-repo probes are removed on every exit path including an interrupt, so a red run cannot leave a token file in the working tree.
- Credential guard: `bash .github/scripts/test-opencode-credential-guard.sh`; a separate PR-gate step. **Runs on bash 3.2 as well as 4+** — the guard's provider-key set was a newline-delimited list rather than a `declare -A` associative array, so the whole security surface is now checkable locally and not only on CI's ubuntu. It covers the environment allowlist, the project-config refusal, the hardened config's deny globs (including the nested `/proc/<pid>/task/<tid>/environ` form and OpenCode's own `~/.local/share/opencode/auth.json`), the checkout-symlink refusal, and the Git credential helper and hook protection. The symlink cases include targets *inside* the checkout that the deny globs name (`.git/config`, the `.git` directory, `.env`, with `.env.example` still accepted), the temporary roots (`/tmp`, `/private/tmp`, `/var/tmp`, `$TMPDIR`), and `/etc`, which resolves to `/private/etc` on macOS — the guard compares each root both as written and resolved. Its benign outside-link case targets `/usr/share`, because the harness's own scratch directory now sits under a sensitive temporary root.
- Data-root smoke: `DATA_ROOT="$HOME/<scratch-dir>" scripts/smoke-apphost-container.sh IMAGE` runs the same lifecycle with the four volumes bound under that folder and asserts reset empties them. Opt-in, not in the PR gate; on Docker Desktop the folder must be under a shared path.
- Controller entrypoint lifecycle: `python3 scripts/test-apphost-entrypoint.py`; engine-free — the Docker transport and the AppHost are mocked, so it needs no daemon, but it does require a built AppHost. Runs in the PR gate's "Test controller preflight and lifecycle" step, and launches the script under the interpreter named by its own shebang rather than a hardcoded `/bin/sh`, which is what lets it detect a reverted shebang at all. **Platform-dependent in exactly one place:** `test_hyphenated_parameter_env_names_reach_the_apphost` fails only against a broken entrypoint where `/bin/sh` is dash — true on the gate's `ubuntu-latest`, false on macOS, where `/bin/sh` is bash in POSIX mode and preserves unnameable env names, so that single test passes against a broken script there. Exercise this harness on Linux before trusting a local macOS run; a green macOS run is not evidence the entrypoint shebang is intact. Its `interpreter()` helper also reads the shebang tail as one argv element, so it cannot execute an `#!/usr/bin/env bash` script — harmless today only because the entrypoint deliberately uses the absolute path recorded in Key Behaviors.
- Real PostgreSQL checks: `python3 scripts/tests/test_ticket_ownership.py --postgres`; disposable pinned AGE container, synthetic pre-migration table only, no published ports or corpus access. Not part of the .NET suite.
- 2026-09-15 verification: 14 tests passed (transport, read-only enforcement, exact/malformed ownership, runbook rollback/commit/stale-input guards and partial-graph refusal); Dockerized ShellCheck (`koalaman/shellcheck:v0.11.0`, read-only mount, network disabled) and Bash syntax checks passed. This does not establish whole-migration or application-suite acceptance.
