# AGENTS.md - Operational Scripts

## TL;DR

Operational checks support operator decisions; a preflight must never repair the corpus it inspects.

## Non-Negotiables

- Ticket ownership preflight is read-only, including against the default dev database. Never weaken the migration's duplicate guard or choose a keeper automatically.
- Exact provider/key and group UUID reports are sensitive operational output, not application logging. Never send them to telemetry, CI artifacts, or commits; credentials stay inside the container.
- API smoke credentials are generated per run, passed through environment variables, used only in
  Authorization headers, and never printed or committed.
- Verification uses a newly created isolated fixture, never the default corpus or a schema cloned from it. Cleanup may remove only resources created by that test invocation.
- Do not turn the manual remediation runbook into an automated destructive cleanup script. Membership ownership is an operator decision; preserving memories does not preserve ticket-based discoverability.

## Key Behaviors

- `run.sh` / `run.ps1` are **operator launchers, not checks**, and are the only scripts here that are meant to be run as a daily entry point rather than as a verification. Each starts exactly one container — the published controller image, which carries the AppHost, DCP and dashboard — and that controller starts the other workloads through the mounted socket. Nothing in this directory may start `mimisbrunnr-<id>-{host,viewer,postgres,blob-well,seq}` directly: their ownership, health and lifecycle rules live in `apphost-container-entrypoint.sh`, and a launcher that bypassed them would re-create open defect #159 (a second controller removing another installation's running workloads). Documented in [CONTROLLER_LAUNCHER.md](CONTROLLER_LAUNCHER.md).
- **Client settings are environment variables, and the write token alone lives in a file (APPHOST LADR-007).** `CONTEXT_MEMORY_BASE_URL`, `CONTEXT_MEMORY_READ_TOKEN` and the decision settings are read by every client from the process environment only. `run.sh` adds each **missing** non-secret setting to a marked block in the shell profile (`MIMIS_PROFILE`, else by login shell; `off` opts out) — **add-only**: a setting already exported, or assigned anywhere in the profile, is never added again or changed, and a run with nothing missing leaves the profile byte-identical. `run.ps1` does the same with Windows User-scope variables. **An existing base URL and existing tokens are the master** (environment, then profile; the write token also from `~/.mimisbrunnr/credentials`): the API is published on the base URL's port — a disagreeing `P_HOST` is refused — and the controller's stored pair is overwritten with the tokens, so every client holding them reaches the Host. **The write token is never exported**: it would reach every process the shell starts and the read client refuses to run beside one, so it lives only in `~/.mimisbrunnr/credentials` (rewritten whole, one key), and a write-token export inside the managed block is removed. The read-only credential file is retired — named, never deleted. For the three engine secrets resolution is still **environment → stored file → generate**, add-only: a `Parameters__*` value supplied through the environment is used and deliberately *not* written to disk. **A credential file the run cannot read, or cannot read as text, is refused rather than rewritten.** **Adoption resolves the two tokens as a matched pair or not at all** — per-key resolution could adopt one and mint the other, the split-pair 403 adoption exists to prevent.
- **`env-export` prints credentials, and `up` never does.** `scripts/run.sh env-export [posix|powershell]` emits `export KEY='v'` or `$env:KEY = 'v'` for the `CONTEXT_MEMORY_*` client settings — each at the value configured (environment, else profile, else default) — and **never the write token or the decision API key**: evaluating the write token would make it ambient. `--profile [FILE]` applies the same add-only block to another profile. Printing is a separate verb on purpose: a token written to a terminal that gets scrolled back, recorded, or read over a shoulder is disclosed. Diagnostics go to **stderr** throughout: stdout is a data channel that `env-export` is captured from, so a status line written there becomes a command the shell tries to run.
- **The launcher must not depend on `openssl`.** `secret()` prefers it and falls back to `/dev/urandom` through `od`. openssl is declared by neither Dockerfile, so relying on it alone made credential generation fail on a minimal image — and the failure surfaced as an *empty credential file*, not as a missing command, which is why it took a second run on a stock `ubuntu` container to read. The same container run found a second defect the developer's machine could not: `adopted` was declared without a value and only ever incremented on the adoption path, so `set -u` aborted on a fresh clone or a container with no provision file. A checkout that has run the provisioner hides that case permanently. **Run `scripts/test-run-launcher.sh` inside a minimal `ubuntu:24.04` container, not only on the development machine** — it has no openssl, and that is the point.
- **`scripts/test-run-launcher.sh` is the harness, and every case runs under `env -i` with a scratch `HOME`, `MIMIS_HOME`, `MIMIS_MACHINE_CREDENTIALS` and `MIMIS_PROFILE`.** The launcher takes the base URL and tokens from the environment and writes the shell profile, so an inherited `CONTEXT_MEMORY_*` name would test the operator's configuration and an inherited `HOME` would edit their real `~/.zshrc`; an unset list silently misses the next such variable, a cleared environment cannot. The machine-credential redirect is the older half of the same rule: a harness that redirected only the home once overwrote live credentials. Every case goes through `run_launcher_in`, whose leading `NAME=value` arguments are the only environment a case gets.
- **Both launchers gate on `/health`.** `up` waits for the API and exits non-zero with the cause ranked, because returning immediately made "the script ran" and "the app started" indistinguishable — one bad postgres password once looked like three session restarts' worth of mystery. Neither launcher may drop this gate.
- **Orphan cleanup keys on `io.smooth-mimisbrunnr.installation`.** A hard kill can leave the five workloads with no controller owning them; the launcher removes exactly those carrying its installation's label, and never a container it does not own. A foreign container on one of the names is refused by the controller's own preflight instead.
- **Two file-safety rules both launchers enforce, both of which a first draft got wrong.** `[ -f ]` follows a symlink, so the "not a regular file" guard has to test the link itself (`-L` / `LinkType`) or it passes a symlinked credential file. And mode 600 is re-asserted on *every* run, not only on creation, because reuse is the quiet path where a file widened by a backup restore would otherwise stay group-readable for the life of the installation. Credentials are written through a temp file and renamed, and a temp file holding a secret is removed on interrupt.
- **The token parameters cannot be exported by a shell.** `Parameters__api-read-token` contains hyphens, so `export`/`VAR=x cmd` is a syntax error in both bash and zsh; use `env 'NAME=value' …` or PowerShell's `$env:` provider. Same property as the `#!/bin/bash` entrypoint shebang below, and the reason the generated secrets must reach the container by `--env-file`.

- `install-skills.sh` / `install-skills.ps1` are the **skills installers** (see
  [SKILLS_INSTALLER.md](SKILLS_INSTALLER.md)), distinct from the two launchers above: they manage the
  folders under `.agents/skills/`, never a container. One contract, two ports, for macOS/Linux/Windows.
  Five properties are the contract and each is pinned by a harness case:
  - **The skills root is searched, never created** — `.agents/skills` → `.claude/skills` → `.codex/skills`,
    first match wins, and **no match is a hard error that writes nothing**. Creating a skills folder the
    operator never asked for is not an install, and a folder that exists by accident then becomes the
    target of every later run. `SKILLS_ROOT` overrides the search.
  - **The installer manages only the owned set — `mimisbrunnr-*`, `ai-understanding`, `ai-brain-dump`,
    `ai-memory-context` (plus `_mimisbrunnr-shared/`, which is infrastructure).** The rule lives in `is_owned_skill()` (bash)
    and `Test-OwnedSkill` (PowerShell); the two must match and the harness holds them to each other.
    Everything else in a target tree — local coding skills, operator experiments — is left byte-identical
    and never enters the manifest, even when a hand-edited manifest names it `installed: true` (the update
    loop refuses unowned names as well as the manifest builder). This is the whole point of the scoping:
    an installer without it pulled a foreign repo's local-only skills into its manifest and marked them
    `installed: true`.
- **`installation.json` is reconciled against the *owned union* of the clone source's skills and the skills
    on disk, and every operator-set flag survives.** New owned skills join as `installed: true`; skills in
    neither the source nor disk — or no longer owned — are dropped; an existing `true`/`false` is carried
    across untouched. **The union is load-bearing and the clone therefore happens *before* the manifest is
    built:** derived from disk alone, a first install into an empty skills folder has nothing to install, so
    the operator's very first run — the one every operator does — reports success and leaves them an empty
    folder with a manifest listing nothing. A first run defaults everything to `true`, because defaulting to
    `false` makes a first run a no-op — the operator would have to hand-edit the manifest before anything
    could ever update.
  - **A manifest that will not parse is a hard error, never a first install.** Treating unparseable as
    absent rebuilds the file from defaults, which silently re-enables every skill the operator had
    switched off — on precisely the file that needs a human. Both ports refuse and leave it untouched.
  - **Only `installed: true` folders are replaced from the clone source.** A `false` skill is never
    overwritten, so a local edit inside one survives every run. The flag governs *updates only*: it
    removes nothing and disables nothing.
  - **The manifest is written after the update, and the update reads the merged manifest.** The manifest
    lives inside `_mimisbrunnr-shared/`, which step 4 refreshes, so writing it first has the refresh
    clobber it; and reading the *pre-existing* manifest means a first install can see which skills it just
    decided to install. Both are single-line orderings that read as interchangeable and are not — the
    PowerShell port shipped the second one and installed nothing on its first run until the harness caught
    it.
- **`_mimisbrunnr-shared/` is reconciled, not merged, and the sweep is recursive.** An updater that only
  ever copies in leaves a file deleted upstream alive forever — and the deleted file is usually the one a
  fix was meant to remove. A **top-level** sweep is not enough either: it keeps every folder the source
  still has while leaving the files *inside* it that the source dropped, which is where a retired script
  actually goes. `installation.json` is spared wherever the sweep finds it, or an interrupted run would
  cost the operator every flag on the next one. This folder refreshes on every run whatever the flags say
  (it is not a skill, never appears in the manifest, and every installed skill that calls a shared script
  is broken without it), and it is **copy-then-sweep rather than replace-the-folder** so the manifest
  inside it cannot be taken down by a later interruption.
- **An installed copy is pruned to what runs: `tests/` and `__pycache__/` go, nothing else does.**
  `prune_non_shippable()` (bash) / `Remove-NonShippable` (ps1), copy-then-remove rather than a
  `tar --exclude` or an `rsync` filter — GNU and BSD spell `--exclude` differently and a filter would be a
  third dependency, while `cp -R` is already there and means the same thing on both platforms. `tests/`
  is excluded because a harness asserts against this repository's own tree (paths, the shared original
  behind a WET copy) and is meaningless outside it; `__pycache__/` is interpreter output, removed
  recursively because an operator running the installed scripts directly leaves one at any depth.
  **The list is two names and must stay two**: `agents/`, `references/` and `assets/` are
  runtime-referenced — odin reads `references/read-path.md` mid-skill, ai-understanding renders
  `assets/UNDERSTANDING.template.md` — so widening it ships a skill documenting a file it cannot open.
  This is a runtime rule, not a security boundary: nothing in a skill reads its own tests. It runs
  **after** the shared-folder sweep, never before, because the sweep compares destination against source
  and needs the same files on both sides. The clone source is never pruned, which is what leaves the
  sweep able to compare against it. A skill marked `installed: false` is never copied and so never
  pruned — its local `tests/` survives untouched.
- **Two self-containment questions are asked by two different gates, and the second is not a subset of
  the first.** `check_vendored_skills.py` (HLD-010 NFR-05) asks whether a skill reaches into *this
  repository's* tree, reading only `*.md`/`*.yaml` and skipping table rows.
  `check_skill_selfcontainment.py` asks whether a skill reaches outside *itself*, which is what decides
  whether it can ship as a zip alone. It must cover **both** mechanisms — a runtime
  `Path(__file__).resolve().parents[N]` resolution, and a command the SKILL.md documents — because the
  second is the one that bites: odin has no shared import anywhere in its own scripts and is still broken
  alone, because its SKILL.md tells the agent to shell out to a sibling. A declared dependency is fine;
  the gate fails only on an **undeclared** one, so `SHARED_DEPENDENT` is the record and adding to it is
  the deliberate act. Two properties that are load-bearing: the runtime scan excludes `tests/`, and it
  scans the file **text** with a window rather than line by line, because saga's resolution wraps across
  two lines and a line-oriented scan reads it as self-contained.
- **Every copy goes through `copy_wet` / `Copy-Wet`: a symlink whose target resolves inside the clone is
  materialised, and one that does not is kept as a link.** The point is a **self-contained installed
  skill** — one that can be zipped and imported into a runtime with no repository behind it. Copying a
  link would ship a pointer into a path the consumer does not have. So a link pointing inside the
  clone (an authoring convenience — one file, two names) is copied as what it points at, while a link
  pointing outside the repo, or one with no target, is copied as a link, because that is the author's
  business and following `/etc/hosts` would pack a system file.
  - **Cycles are kept as links**, which is what makes the run terminate: a link to its own ancestor, or
    to something already being expanded, would otherwise recurse forever. The expansion stack stops at
    a repeat, leaving the link visible rather than materialising a loop.
  - **`CLONE_ROOT` is assigned unconditionally at script scope and only ever from this run's clone, and
    it is canonicalised.** An inherited `CLONE_ROOT` would widen "inside the clone" to a path the caller
    chose. Canonicalisation is not tidiness: `mktemp -d` returns the *unresolved* path — on macOS
    `/var/folders/…`, which `cd -P` reports as `/private/var/folders/…` — while every path `copy_wet`
    compares against it has been through `real_path`. With the two spellings differing, `inside_clone`
    is always false and **every** symlink is copied as a link: the exact failure the mechanism prevents,
    invisible on Linux because `/tmp` is not a symlink. The harness case that caught it is why the
    fixture runs on macOS paths.
  - **`real_path` resolves by hand, not with `readlink -f`** (GNU-only; BSD/macOS lack it) — follow the
    final component with `readlink` in a bounded loop, then `cd -P` the directory. The `cd -P` on a
    directory is what makes a `self -> .` link canonicalise to the folder itself and therefore match the
    expansion stack; without it the path keeps a `/.` tail, never compares equal, and the cycle is
    materialised instead of kept.
  - **The sweep distinguishes a dangling link from an absent one.** `-e`/`Test-Path` follow links, so a
    broken link reads as absent on *both* sides: the sweep would delete one the source still has, and
    could not tell it from one the source deleted — a retired link living forever, which is the bug the
    recursive sweep exists to prevent, with a symlink instead of a file.
  - **ps1 uses `LinkTarget`, not `LinkType`** (hence the `#requires -Version 7.2` floor): `LinkType` also
    reports `HardLink`, so testing it would recurse into a hard link as though it were a symlink and
    materialise it, turning a shared file into a duplicate per consumer. `Test-Symlink` guards `$null`,
    which is load-bearing under `Set-StrictMode -Version Latest`: reading a property off `$null` throws
    there, and the sweep asks about paths that may not exist, so without the guard the first missing entry
    aborted the whole sweep and every stale file below it survived.
- **Per-repo mode installs no rules and no hooks; `-g` has the machinery for both and owns neither.** There is
  no `<agent-root>/rules/` destination and no `rules -> ../.github/instructions` link to write through in
  per-repo mode — the repo *has* that symlink (`.agents/rules`), but it is a repository artefact, and the rules
  and hooks it holds belong to smooth-devex-template. `OWNED_RULES` / `OWNED_HOOKS` are therefore **empty**, in
  both ports, and `-r` / `-h` / `--uninstall` are refused without `-g` rather than silently ignored. Owning a real
  rule or hook is adding its name to the list in both ports; the harness drives the machinery with synthetic
  names through `SKILLS_TEST_OWNED_RULES_EXTRA` / `SKILLS_TEST_OWNED_HOOKS_EXTRA` (production never sets them).
- **`-g` installs machine-wide into `~/.smooth-ai-mimisbrunnr` and wires Claude Code, Codex and OpenCode** (what goes where, and why the store and the edits are shaped this way: [SKILLS_INSTALLER.md](SKILLS_INSTALLER.md) → *Global install*). The traps an agent editing it will not see from the code:
  - **Never point it at `~/.smooth-ai-devex`, reuse smooth-devex-template's block markers or `.smooth-devex-*` snapshot suffix, or restore a snapshot over a shared config file on uninstall.** That installer edits the same three files and purges links by store prefix; each of those turns one installer into a deleter of the other's work.
  - **A default run parses no operator config.** With the owned lists empty, `AGENTS.md`, `hooks.json` and `opencode.json` are not parsed, snapshotted or created, so an `opencode.json` with `//` comments must not fail a skills install. Parsing is strict when it does happen (PowerShell checks with `System.Text.Json` first, and passes `-DateKind String` where it exists), because `ConvertFrom-Json` accepts comments and rewrites date-like strings into local time.
  - **The store path has one spelling.** Links are recorded and matched as strings, so bash strips trailing slashes; PowerShell needs nothing because every path goes through `Join-Path`.
  - **Tool variables are the tools' own** (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME`); `OPENCODE_CONFIG` is a config-file path to OpenCode and is not used.
  - **PowerShell variables are case-insensitive.** A local `$wanted` beside a parameter `$Wanted` is one variable; it silently emptied the rule list and only the cross-port case caught it.
- `release_policy.py` permits publication only for `push` on `refs/heads/main`. PRs, tag pushes, releases, and manual dispatch fail closed. Candidates include source SHA/run/attempt; stale main builds cannot promote `latest`. No version-tag or GitHub Release creation path remains.
- A clean snapshot is not a reservation: writers must remain stopped from the final precheck through migration. Host startup applies migrations, so checking after startup is too late.
- Same-group repeated memberships are not cross-group ownership conflicts. Malformed containers or identity types block preflight even though some live reads treat them as absent; silently skipping them would claim migration readiness without establishing it.
- The checker needs only `public.memory_group`, not AGE or the ticket migration. The [ticket migration runbook](../docs/hlds/003-graph-edges-on-age/ticket-migration-runbook.md) targets legacy data before graph backfill; it refuses installed/partially installed ticket graph objects.
- The one-shot `restore` verb's built-in reconciliation supersedes `scripts/verify-graph-restore.sh` for the HLD 001 NFR-03 round-trip: it restores both stores from a self-verifying snapshot archive and prints a reconciliation (counts, blob resolution, bounded traversal) instead of `pg_dump`/`pg_restore` around `docker exec`. `verify-graph-restore.sh` remains for a lighter graph-only round-trip and `seed-graph-sample.sh` still seeds the NFR-03/NFR-04 checks; the separate NFR-04 pre-upgrade check (`verify-graph-preupgrade.sh`) is unaffected.
- `apphost-container-entrypoint.sh` declares `#!/bin/bash` rather than the `#!/usr/bin/env bash` used by the other scripts in `scripts/`. **That divergence is deliberate; do not normalise it away.** `Dockerfile.apphost` installs the script as `/usr/local/bin/mimisbrunnr-orchestrator` and makes it the container `ENTRYPOINT`, so the shebang *is* the interpreter selection, and an absolute path avoids depending on `env` being on `PATH` at exec. The choice is load-bearing rather than cosmetic: the engine hands the controller `Parameters__api-read-token` / `Parameters__api-write-token`, and dash drops env names that are not shell identifiers — the silent cause of every failed publish between 2026-09-17 and 2026-10-01 (see the changelog). **The consequence to carry forward is that `/bin/bash` is a base-image requirement of `mcr.microsoft.com/dotnet/aspnet:10.0`, not an assumption:** a bash-less aspnet-derived base would fail at container start rather than degrade, and the aspnet image's shell inventory is asserted nowhere in this repository — the publish-image smoke is the only check that would catch it, so treat a base-image change as a publish-blocking change until that smoke runs.
- `provision-credentials.sh` writes the API Bearer tokens to **two** gitignored env files, split by parser grammar: `.context/mimisbrunnr.env` is sourceable and carries only valid shell identifiers (the server `ApiAccess__*` names and the skill `CONTEXT_MEMORY_*` names), and `.context/mimisbrunnr.env.controller` carries the `Parameters__*` names for the published controller's `--env-file` — those names are not shell identifiers, so keeping them in the sourceable file makes `set -a && source` print a token as "command not found". Both files carry the same token values, so the service and the host-side skills still read one source of truth. Idempotent once the pair exists: re-runs reuse the existing values, `--rotate` regenerates, and a pre-split single file (no `.controller`, or still carrying `Parameters__*` lines) is rewritten into the pair rather than silently kept — re-splitting carries the file's existing token values forward, so the documented no-`--rotate` path never rotates a token a running Host already holds. Only a missing file or an explicit `--rotate` regenerates. Mode 600, re-asserted on every reuse run, not only on create. The tokens are runtime configuration only and never touch the store, so rotating them invalidates no data.
- **`provision-credentials.sh` and `run.sh` treat the same key differently, and the difference is which side owns it.** The provisioner **preserves** an existing base URL in `.context/mimisbrunnr.env` because that file is a checkout-local provisioning artefact. `run.sh` takes an existing `CONTEXT_MEMORY_BASE_URL` in the operator's environment or profile as the **master** that decides the port a running installation publishes. Read either script alone and the other looks like a bug; this bullet is the place that says so.
- `provision-credentials.sh --base-url` is **shell input**, because consumers `source` the file it lands in: it must be a bare `http(s)` origin (host name, IPv4 or bracketed IPv6, optional port), and anything else — userinfo, a path, `$(…)`, a backtick, `;`, whitespace — is refused without being echoed. The line stays **unquoted on purpose**: the same file is the standalone Host's `docker run --env-file`, which keeps quote characters as part of the value, so validation (whose accepted character set has nothing a shell assignment expands) is the defence, not quoting. A file's existing base URL is kept across a re-split and a `--rotate` that do not name one (re-validated, refused if hand-edited into something else), and naming a different one rewrites the pair keeping the tokens. `--rotate --skip-apphost` warns loudly when the AppHost user secrets still hold the previous pair, checking key names only. A temp file that may hold a token is removed on exit and on `HUP`/`INT`/`TERM`.

## Test References

- **The installer's owned set is stated in four places, and four is one too many for a human to hold.** `is_owned_skill()` (bash), `Test-OwnedSkill` (ps1) and `OWNED` in `check_skill_selfcontainment.py` are three copies that the parity cases hold to each other, so an addition missing one of them turns the harness red. The fourth is `pr-gate.yml`'s `paths:` filter — **which decides whether the gate runs at all** — and it had nothing holding it. That is not a hypothetical: `ai-memory-context` was added to all three derived copies and to the gate's *step list*, and omitted from the filter, so its harness at `:120` was unreachable and a PR touching only that folder started nothing and said nothing. GitHub evaluates `paths:` before a runner exists, so the filter **cannot be derived** the way the other three are; it has to be asserted, which is what `test_the_gate_triggers_on_every_owned_skill` does. The filter also reads the prefixed skills as one `mimisbrunnr-*/**` glob rather than a line per skill — the same shape `agile-github-*` already used — so the next prefixed skill is covered by the form of the filter rather than by a remembered edit, and the parity case proves it with a name that does not exist yet.
  - Skills installer: `bash scripts/test-install-skills.sh`; runs in the PR gate's "Test skills installer" step. 101 cases across both ports (50 when `pwsh` is absent, as on the gate runner): first-run creation (owned catalogue only, unowned disk skills excluded), reconcile (drop/add/flag-preservation, unowned never listed), the write-ordering property, an `installed: true` folder replaced from the clone source, an `installed: false` folder **not** overwritten, an unowned skill left byte-identical + unlisted + un-installable even via a hand-edited manifest, a corrupt manifest refused and left untouched, the root search order (`.claude/skills` beating `.codex/skills`), no-skills-directory as a non-zero exit that creates nothing, and the recursive stale sweep sparing `installation.json`. **No network and no container engine** — the clone source is the checkout itself (`SKILLS_REPO` = the repo, `SKILLS_BRANCH` = the current branch), so a red run is about the code and not about GitHub. The per-repo cases force `SKILLS_ROOT` to a scratch tree, so a red run cannot touch the checkout's own `.agents/skills`; the `-g` cases clear it and pin the working directory instead (below).
  - **The 23 `-g` cases per port (plus a cross-port parity case and an owned-list parity case) run each scenario in a throwaway `HOME` with every location pinned** (`HOME`, `SMOOTH_MIMISBRUNNR_HOME`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME`) **and from that directory as the working directory**, against a fixture source repo built by the harness rather than the checkout — this repo owns no rules or hooks, so the machinery is driven with synthetic names through the test-only variables. The working-directory pin is not tidiness: a mutation that let `-r` through without `-g` fell into per-repo mode, found the *checkout's* `.agents/skills`, and overwrote `_mimisbrunnr-shared` and `ai-brain-dump` with the fixture's. Coverage: links and the shared folder per tool, no config file created or parsed by a default run, idempotent re-run, foreign entries kept, refusals writing nothing, corrupt/empty manifest, skill/rule/hook flags, tool off (including an unrecorded link), category narrowing, snapshots taken once, uninstall restoring operator bytes and leaving a template installer's block/hook/instruction intact, an unparseable `opencode.json` or `hooks.json` refused and untouched, and both ports writing the same bytes.
  - **One case exists because a real end-to-end run failed while the harness was green:** a first install into an *empty* skills folder. Every harness case had planted skills on disk first, so the disk-only catalogue was never exercised where it matters — the operator's first run. The harness now plants nothing and asserts the source's skills actually land.
  - **The `ps1` and parity cases are skipped with a stated reason when `pwsh` is absent**, which is the case on the `ubuntu-latest` gate runner. They are exercised locally where `pwsh` is present. **That gap is not cosmetic:** the PowerShell-only failures this file's contract already records are exactly the ones a Linux run cannot see — the `.ToString('yyyy-MM-ddTHH:mm:ssZ')` timestamp that rendered `2026-10-15T13.10.10Z` under one locale because `T` is a .NET format *modifier*, and `ConvertTo-Json` unrolling a single-element `skills` array into a bare object, so a one-skill tree would hand the next run a different shape. Treat a green gate run as covering the bash port only, and re-run locally with `pwsh` present before trusting a change to either port. Verified green on macOS (bash 3.2, `pwsh` present — 101/101) and on GNU/Linux in `ubuntu:24.04` (`pwsh` absent — 50/50). Every mutation applied to a contract property was checked to fail the harness.
